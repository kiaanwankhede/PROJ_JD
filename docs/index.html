A1

How it is defined

Job descriptions are defined in Job Profile Builder, part of SuccessFactors.

A job description is defined against a job role. It is part of a job profile, which is created for a family, a role or a position. Without Job Profile Builder there is no description per role; it exists only on each job requisition.

Admin, no approval

A2

How it is attached to the JD

How a role's job profile becomes the job description on a job requisition (the request to fill a job).

The requisition gets a copy of the role's job profile. Everyone hiring for the same role starts from the same copy. After that, each requisition can be edited on its own.

Three ways the profile is attached

  1. Browse Families & Roles: the recruiter picks a family and role, previews its profile, and selects it.
  2. From a position: a requisition started from a to-be-hired position in the org chart gets that position's role and profile.
  3. By import: a requisition imported with a role and a blank description gets the role's profile filled in.

How Enhance Job Description works

  1. Save the requisition. The AI only reads saved data.
  2. Click Enhance Job Description (on the Job Profile tab when Job Profile Builder is used).
  3. Accept the AI usage notice. It returns after every sign-in.
  4. Compare current and generated text side by side; with Job Profile Builder, section by section.
  5. Accept or discard. To try again, edit fields by hand and click again.

Solution to build

A role-level job description service on SAP BTP for six requirements: prompt-based create or enhance, market research, learning from past hires, one JD for many requisitions, different JDs for different hiring managers, and HR updates against the job role.

B0

Requirements

The original brief rewritten as requirements a team can build and test against.

Is the brief realistic? The problems are real: SAP's enhancement works one requisition at a time, hiring managers want their own versions, and HR needs control at role level. As written, though, it reads like a case study. It has no goal or measures, no scope, no acceptance criteria and no edge cases. Its riskiest line, learning from past hires, needs privacy and bias safeguards.

Decisions the business must make first

  • Who owns the role master: HR, Talent Acquisition or the compensation team?
  • Is a version per person, per team, per location or per position?
  • Keep or drop SAP's Enhance Job Description licence once this is live?
  • Which market data source and budget (for example Lightcast or Adzuna)?
  • Is using hire data approved, and in which countries?
  • Which countries' pay-transparency rules apply?
The solution in five decisions
  1. Manage the JD at role level, not requisition level. The role's Job Profile Builder profile is the HR-owned master. The assistant keeps versions of it.
  2. Hiring managers get variants, stored as patches. A variant holds only section-level changes on top of a master version. Locked sections cannot be patched.
  3. Requisition JDs are rendered, not generated. AI runs once per master or variant. Each requisition is filled deterministically from master + variant + requisition facts, so ten requisitions cost one AI call.
  4. Sync is event-driven. SuccessFactors' “Update of Job Requisition” event triggers the assistant, which writes the JD back through the OData API. A fingerprint stops repeat work and loops.
  5. Drafting is grounded. Every draft uses the master, a monthly market benchmark and an anonymous profile of recent hires, through AI Core orchestration with data masking and a JSON output schema.

The JD model

One canonical JSON shape for masters, drafts and rendered JDs. Section keys match Job Profile Builder content, so the JSON maps straight back to JobProfile.

Master (HR)Full JD per role, locale and version. Some sections locked.
Variant patch (manager)List of section operations on one master version.
Rendered JD (requisition)Master + patch + requisition facts. Written to SuccessFactors.

Resolution rule: which JD a requisition gets

def resolve(role_id, locale, manager, location, org):
    for scope in [("MANAGER_LOCATION", manager, location),
                  ("MANAGER", manager), ("ORG", org),
                  ("LOCATION", location)]:
        v = store.approved_variant(role_id, locale, scope)
        if v: return master(role_id, v.base_version), v
    return latest_master(role_id, locale), None

Fingerprint: skip work that is already done

fp = sha256("|".join([role_id, locale,
        str(master.version), variant_id or "-",
        str(variant_version or 0), location,
        salary_range, work_model]))
if link.fingerprint == fp:
    return  # nothing changed, no write, no loop

Database (HANA Cloud)

JSON in NCLOB columns; embeddings in REAL_VECTOR (dimension depends on the embedding model you deploy).

CREATE TABLE JD_MASTER (
  ROLE_ID NVARCHAR(40), LOCALE NVARCHAR(10), VERSION INTEGER,
  JPB_PROFILE_CODE NVARCHAR(40), SECTIONS NCLOB, STATUS NVARCHAR(20),   -- DRAFT | IN_APPROVAL | ACTIVE | RETIRED
  CHANGE_NOTE NVARCHAR(1000), CREATED_BY NVARCHAR(100), CREATED_AT TIMESTAMP,

CREATE TABLE JD_VARIANT (

B5

How each requirement is implemented

1

Create or enhance a JD with a prompt

The manager talks to the Joule agent. The agent calls draft_jd with a mode (create, enhance, refine) and the manager's instruction. The service builds grounded context, calls AI Core orchestration once, validates the JSON and returns a draft. Refinements reuse the draft id, so each turn sends only the delta instruction.

  1. Resolve the role: find_role("Senior ABAP Developer") searches RoleEntity names cached in HANA.
  2. Load context: active master (or the manager's variant), market benchmark for role + location, hire profile.
  3. Call orchestration with the template below, masking on, response format = JD JSON schema, temperature 0.3.
  4. Run checks: locked sections unchanged, mandatory skills present, inclusive-language scan, salary range present where the country requires it.
  5. Store as JD_VARIANT with status DRAFT; the agent shows a summary of changes and asks “Save and apply?”.

config = OrchestrationConfig(template=template, data_masking=masking,
    llm=LLM(name=DEPLOYED_MODEL, parameters={"temperature": 0.3}))

result = OrchestrationService(config=config).run(template_values=[
    TemplateValue("mode", mode), TemplateValue("master", master_json), ...])
draft = JDSchema.model_validate_json(result.orchestration_result.choices[0].message.content)

The SDK also ships an orchestration_v2 package with the same concepts and a ResponseFormatJsonSchema class for strict JSON output. Pin one version in requirements.txt and align imports to it.

2

Market research for a best-in-class JD

A monthly job per active role and location pulls 50–200 similar postings from a job-market API, extracts structured facts with the LLM, aggregates them and stores only the aggregate in MARKET_BENCHMARK. Drafts use it as evidence; the review screen shows gaps.

  1. Search: role name + synonyms (from the role's job codes) + location. Example with Adzuna's developer API: GET /v1/api/jobs/in/search/1?what=sap+abap+developer&where=pune&results_per_page=50 through a BTP destination holding app_id and app_key. For enterprise use, Lightcast's licensed postings API gives deduplicated data with normalized skills.
  2. Extract each posting with a small JSON schema: skills[], responsibilities[], years_experience, seniority, salary_min/max, work_model.
  3. Normalize skills against your Talent Intelligence Hub skill library (or Lightcast Open Skills), so “ABAP OO” and “Object-oriented ABAP” count once.
  4. Aggregate: a skill in ≥ 30% of postings is market standard; 10–30% is a differentiator; salary P25 / P50 / P75 where posted.
  5. Store and discard: keep counts, percentiles and source URLs; discard posting text after extraction.
  6. Use: passed to drafting as evidence; the review screen shows “Market standard skills missing from this JD: S/4HANA migration (64%)”.

Rule: only sources whose terms allow this use. No scraping of LinkedIn or job boards that forbid it. Never reuse competitor wording.

3

Learn from the last hires for the role

A monthly job (and the “Update of Job Application Status” event) rebuilds an anonymous HIRE_PROFILE per role from the last 24 months of hires. Only aggregates are stored, and only when there are at least 5 hires.

  1. Find requisitions for the role: JobRequisition filtered on jobRoleEntity/externalCode; keep jobReqIds.
  2. Find hires: JobApplication for those requisitions where hiredOn is set; skip anonymized applications.
  3. Read the resume (jobApplicationResume) and candidate background; mask personal data in orchestration; extract skills, years_experience, certifications, education_level, industries as JSON.
  4. Aggregate: report an attribute only if ≥ 3 hires share it; output frequencies and medians (“7 of 9 had SAP BTP; median 6 years ABAP”).
  5. Delete per-person extractions after aggregation; keep HIRE_PROFILE and an audit entry.
  6. Bias check: never extract gender, age, nationality or photos; warn HR if one pattern covers 100% of hires (a sign of narrow hiring, not a requirement).

Before go-live: HR and legal sign-off for this purpose under India's DPDP Act 2023 (and GDPR for EU data); add it to the candidate privacy statement.

4

Same hiring manager, many requisitions for the role

No, it is not enhanced per requisition. The manager's approved variant is rendered into each requisition without AI. A new requisition is synced automatically; existing ones are updated in one step.

Event-driven sync

  1. In Integration Center, create an event-triggered integration on Intelligent Services event Update of Job Requisition that calls POST /events/requisition through a destination (OAuth). Fallback: Job Scheduling Service calls /jobs/poll-requisitions every 10 minutes, querying requisitions changed since the last run.
  2. The webhook loads the requisition: role (jobRoleEntity/externalCode), hiring manager (hiringManager), location, locale, posting status.
  3. Ignore it if the role has no managed master, or if lastModifiedBy is the assistant's technical user.
  4. resolve() picks master + variant; compute the fingerprint; stop if unchanged.
  5. render() fills placeholders from requisition facts and produces HTML per section.
  6. Write: templates without Job Profile Builder → JobRequisitionLocale.jobDescription and externalJobDescription (nested under JobRequisition upsert); templates with Job Profile Builder → the requisition's JobProfile (subModule = jobReqProfile) ◐ S2.
  7. Save REQ_JD_LINK and an audit entry.

Existing requisitions

Joule: “Apply my Senior ABAP JD to all my open requisitions” → list_my_requisitions(role) → shows 3 open → manager confirms → apply_jd(variant, [2041, 2042, 2050]). One AI call happened when the variant was drafted; zero during apply.

5

Different hiring managers want different JDs

Each manager has their own variant (scope MANAGER or MANAGER_LOCATION) on the same master. Patches are validated against a section policy, scored for deviation, and auto-approved or routed to HR.

SectionManager may
summary, long_description, team_contextreplace
skills_niceadd_item, remove_item
responsibilitiesadd_item only (cannot remove HR's items)
skills_required, education, employment_conditions, legal header/footernothing (locked)
 
def deviation_ok(master, variant_rendered):
    if not locked_sections_equal(master, variant_rendered): return False, "locked changed"
    if not set(master.required_skills) <= set(variant_rendered.skills): return False, "skill removed"
    sim = cosine(embed(master.text), embed(variant_rendered.text))   # HANA REAL_VECTOR
    growth = len(variant_rendered.text) / len(master.text)
    if sim >= 0.85 and 0.7 <= growth <= 1.4: return True, "auto-approve"
    return False, "HR review"          # → SAP Build Process Automation approval task

Thresholds (0.85, ±30–40%) are starting values; tune them on real variants in Phase 1. Only one approved variant per role + scope; a new approval retires the old one.

6

HR Head updates the JD for the job role

HR edits the master (by prompt or directly). On approval the assistant writes it to the role's JobProfile, bumps the master version, rebases every variant and re-renders requisitions by policy.

  1. HR: “Add GenAI on BTP to Senior ABAP responsibilities.” → update_master(role, instruction) creates master v4 as DRAFT (only HR scope can call it).
  2. Approval in Build Process Automation, or Job Profile Builder's own workflow if you prefer to keep approvals in SuccessFactors.
  3. Write back: JobProfile UPSERT for the role profile: longDescriptions, shortDescriptions, jobResponsibilityContents, skillContents per locale. Status ACTIVE.
  4. Rebase variants on v3: if none of a variant's patched sections changed in v4, set base_version = 4 automatically. If a patched section changed, run a merge prompt (old master section, new master section, manager's version) and set NEEDS_REBASE for the manager to accept in Joule.
  5. Re-render requisitions: open and unposted → write automatically; posted → PENDING_RECRUITER task, because changing a live ad needs a human; closed → leave alone.
  6. New requisitions that pick the role in SuccessFactors get v4 natively, because the role's profile itself changed.
