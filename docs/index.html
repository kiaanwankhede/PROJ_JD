A1

How it is defined

Job descriptions are defined in Job Profile Builder, part of SuccessFactors.

A job description is defined against a job role. It is part of a job profile, which is created for a family, a role or a position. Without Job Profile Builder there is no description per role; it exists only on each job requisition.

How it is attached to the JD

How a role's job profile becomes the job description on a job requisition (the request to fill a job).

The requisition gets a copy of the role's job profile. Everyone hiring for the same role starts from the same copy. After that, each requisition can be edited on its own.

Three ways the profile is attached

  1. Browse Families & Roles: the recruiter picks a family and role, previews its profile, and selects it.
  2. From a position: a requisition started from a to-be-hired position in the org chart gets that position's role and profile.
  3. By import: a requisition imported with a role and a blank description gets the role's profile filled in.

On the requisition

What can change

  • Edit section text and title; add items from the library; add new sections.
  • Show each section on internal postings, external postings, or both.
  • Edits stay on that requisition and never change the library.
  • Picking a different role overwrites all edits, after a warning.
Without Job Profile Builder

Plain text fields instead

  • Internal and external job description, typed or pasted, per language.
  • Header and footer picked from admin templates.
  • Or copy an existing requisition.

Text format: formatted on screen, HTML underneath

What the user sees
  • A rich-text editor with bold, italics and bullets. Users type formatted text, not HTML.
  • Inline images, CSS and HTML code are not supported in the job description field; the editor creates the HTML tags itself.
  • Text pasted straight from Word causes errors on the career site; SAP says to use Paste as Plain Text.
  • Job profile templates use the same rich-text editing.
What is stored and sent by the API
  • JobRequisitionLocale.jobDescription and externalJobDescription hold HTML strings, for example <p>…</p><ul><li>…</li></ul>.
  • Job profile text (longDescriptions and similar) comes from the same editor, so expect HTML there too.
  • SAP's AI feature lists rich text (rte) among the field types it reads.

How Enhance Job Description works

  1. Save the requisition. The AI only reads saved data.
  2. Click Enhance Job Description (on the Job Profile tab when Job Profile Builder is used).
  3. Accept the AI usage notice. It returns after every sign-in.
  4. Compare current and generated text side by side; with Job Profile Builder, section by section.
  5. Accept or discard. To try again, edit fields by hand and click again.

The first design, checked again against SAP's documentation: what changed and why.

R1

What the review found

Everything from the first version was checked again against SAP's documentation. Seventeen findings changed the solution.

In short: the core idea holds (one HR-owned master per role, manager variants, requisitions filled without re-running AI). What changed: Joule cannot carry the user's identity, so writes move to a signed-in review page; SuccessFactors already copies the profile into new requisitions, so the assistant writes less; people's manual edits are protected; edits made directly in SuccessFactors are picked up; SAP's recruiting direction (SmartRecruiters) is handled; and the plan now starts from a mock SuccessFactors because you have no tenant.

B0

Requirements

The original brief rewritten as requirements a team can build and test against.

Is the brief realistic? The problems are real: SAP's enhancement works one requisition at a time, hiring managers want their own versions, and HR needs control at role level. As written, though, it reads like a case study. It has no goal or measures, no scope, no acceptance criteria and no edge cases. Its riskiest line, learning from past hires, needs privacy and bias safeguards.

The solution end to end: eight decisions, the big picture, then five flows. Each flow has a sequence diagram and numbered steps that match it.

H1

Eight design decisions

Everything in the flows below follows from these.

  1. The role master lives in Job Profile Builder. SuccessFactors stays the system of record; the assistant keeps versions and drafts. Edits made directly in SuccessFactors are imported every night.
  2. Manager variants are patches stored in HANA Cloud. SuccessFactors has no per-manager JD, so the assistant adds that layer. HR-locked sections cannot be patched.
  3. SuccessFactors copies the master into new requisitions itself. The assistant writes only when a variant, another language or a placeholder makes the requisition different, and never over a person's edit.
  4. AI runs only when content is created: a draft, a refinement, a master change, a translation or a merge. Filling requisitions needs no AI.
  5. Joule is the conversation; the review page is where things change. Joule tools only read and draft, because SAP does not pass the user's identity to MCP servers. Approving and applying happen in a page where the user signs in.
  6. Everything is keyed by SuccessFactors IDs. Names are used only for display, search and the JD text.
  7. The requisition side sits behind an adapter: SuccessFactors Recruiting now, SmartRecruiters later.
  8. Evidence is optional and governed: market benchmarks by default; past-hire patterns only after legal approval.

D3

Joule, the review page and identity

Why Joule only drafts, and how the real user is known when something changes.

What SAP's Joule Studio docs say about MCP servers

  • An MCP server is added to a Joule agent through a BTP destination: streamable HTTPS, additional property sap-joule-studio-mcp-server = true, and a URL that does not end in /mcp.
  • The destination must exist in both the Joule Studio subaccount and the Joule subaccount, with the same name.
  • Authentication: client credentials (recommended), basic, JWT bearer. Principal propagation and SAML bearer: not supported. ✓

So every MCP call reaches the service as a technical user, never as the person typing in Joule.

Identity rules in this design

  • Joule tools only read and draft. A draft records who asked, but that is only a claim, used to route the draft.
  • Approving and applying happen in the review page. The user signs in through IAS behind the SAP Application Router (configuration, no code); XSUAA scopes decide what they may do.
  • In the review page the service calls SuccessFactors as the signed-in user (principal propagation from BTP), so SuccessFactors' own permissions decide which requisitions they see and may change.
  • At approval, a variant's scope is set from the signed-in user, not from the claim. A draft can be approved only by the person it names, or by HR.
  • Writes that follow an earlier approval (events, re-render after a master change, apply after HR approval) use the technical user.

Write decision (flow F2, step 7)

def decide(req, link, master, variant):
    """Every value is an ID, a version or a hash; names are never compared."""
    if link and link.fingerprint == fingerprint(req, master, variant):
        return "SKIP"                 # nothing changed: no write, no loop
    if link and sha256(req.jd_text) != link.known_hash:
        return "MANUAL_EDIT"          # a person changed the JD: never overwrite
    if (TENANT.jpb_on_requisitions and variant is None
            and not master.placeholders and req.locale in master.locales
            and (link is None or link.master_version == master.version)):
        return "NATIVE"               # SuccessFactors' own copy is already right
    if req.posted:
        return "PENDING_RECRUITER"    # a live ad: a recruiter decides
    return "SYNCED"                   # render, write, read back, store the new hash

After every write the adapter reads the JD back and stores the hash of what SuccessFactors kept, in the same request, because SuccessFactors may tidy the HTML. For NATIVE, the hash of the text first seen is stored.

  • Without Job Profile Builder, render writes jobDescription and externalJobDescription. With it, each section's “Show in internal / external posting” setting does the same job (see A2).

    items = [i if isinstance(i, str) else i["name"] for i in section.get("items", [])]
    if items:
        html += "<ul>" + "".join(f"<li>{escape(i)}</li>" for i in items) + "</ul>"
    return html   # escape(): text from the model can never add its own tags

Which tags the requisition editor and the career site keep is real-tenant check S2 ◐.

Deviation check (approve or send to HR)

def deviation_ok(master, rendered):
    if not locked_sections_equal(master, rendered): return False, "locked changed"
    if not set(master.required_skills) <= set(rendered.skills): return False, "skill removed"
    sim = cosine(embed(master.text), embed(rendered.text))   # HANA REAL_VECTOR
    growth = len(rendered.text) / len(master.text)
    if sim >= 0.85 and 0.7 <= growth <= 1.4: return True, "APPROVED"
    return False, "PENDING_HR"        # HR decides in the review page

Thresholds are starting values; tune them on real variants in Phase 1.

Guardrails

  • Untrusted text (profiles, resumes, postings) is passed as data, never as instructions.
  • Output must match the JD JSON schema; anything else is rejected.
  • Personal data masked and content filtering on in every call.
  • Checks run after every draft: locked sections, required skills, inclusive language, pay transparency, length.
  • No posting or Job Profile Builder change without a signed-in person approving it.

Evaluation

  • A fixed set of 30 cases: roles × modes (create, enhance, refine, master change, merge) × languages.
  • Measured: JSON schema pass (target 100%), checks pass (target 95%), HR rubric score for accuracy, clarity, inclusiveness and market coverage (target 4 of 5).
  • A model grades the rubric; HR spot-checks a sample each run.
  • Rerun and stored in EVAL_RUN before any prompt or model change.
D7

Evidence rules: market and past hires

The rules behind flow F4. In the portfolio build both run on synthetic data.

Market benchmark

  • Search words: the role's names and job code titles plus the city. Results are stored by role ID, country and location code.
  • Licensed sources only, for example Adzuna's developer API or Lightcast. No scraping of LinkedIn or job boards that forbid it.
  • AI Core reads about 20 postings per call into a small schema: skills, responsibilities, years, seniority, salary, work model.
  • Skills are matched to the Talent Intelligence Hub library, so “ABAP OO” and “Object-oriented ABAP” count once.
  • A skill in 30% or more of postings is market standard; 10 to 30% is a differentiator. Salary P25, P50 and P75 where posted.
  • Only counts, percentiles and source links are kept. Posting text is discarded and competitor wording is never reused.

Past-hire patterns (optional)

  • Off by default. Switched on per country after HR and legal sign-off (India's DPDP Act 2023, GDPR for EU data) and a line in the candidate privacy statement.
  • Hires: JobApplication with hiredOn set, for the role's requisitions in the last 24 months; anonymized applications are skipped.
  • Extracted with personal data masked: skills, years of experience, certifications, education level, industries. Never gender, age, nationality or photos.
  • A profile needs at least 5 hires, and an attribute is shown only if 3 or more hires share it.
  • Per-person extractions are deleted after aggregation.
  • HR is warned when one pattern covers every hire: a sign of narrow hiring, not a requirement.

D9

Security and permissions

SuccessFactors API permissions

  • Recruiting: OData API Requisition Export / Create / Update ✓ for the technical user. Managers and recruiters may need it too, because review-page calls run as them (check S5) ◐
  • Job Profile Builder: Manage Job Profile Content (roles) and Manage Job & Skill Profile Visibility → Job Profile (profiles) ✓; HR Heads need edit rights to write masters.
  • The requisition template's field permissions still apply to calls made as a user: a manager may lose edit rights after approval (A2).
  • Applications, resumes and candidate background: technical user only, and only if past-hire patterns are on ◐

BTP connections and roles

  • JD_MCP: Joule → service, client credentials (SAP's recommendation for MCP), in both the Joule Studio and Joule subaccounts.
  • SFSF_USER: review page → SuccessFactors as the signed-in user (OAuth2 SAML bearer, principal propagation).
  • SFSF_TECH: events, nightly sync, re-render after approval, evidence jobs.
  • XSUAA scopes JD.Manager, JD.HR, JD.Admin; HR approval needs JD.HR.
  • AI Core and HANA credentials from service bindings, never in code; every action in AUDIT_LOG with its channel.
